## 1. O que é o projeto

## 4. Processo: resumo de `docs/agents/ciclo-de-desenvolvimento.md`

Cada issue `ready-for-agent` passa por estas etapas:

1. **Worktree e banco:** uma worktree por issue, a partir do `develop`. Copie o `.env` da checkout principal. Cada worktree usa um **banco próprio**, criado com `docker exec trippy-postgres-1 createdb -U trippy trippy_w<nº>`.
2. **Planejador:** publica o plano como comentário na issue.
   - Tarefas do Claude: Opus 5.5, effort medium.
   - Tarefas do Codex: `gpt-6.1-sol`, effort low.
3. **Implementadores:** `gpt-6-luna`, effort xhigh, seguindo a skill `/implement`. Trabalham em paralelo só quando as subtarefas mexem em arquivos diferentes, cada uma em worktree filha.
4. **Revisor:** `gpt-6.1-sol`, effort low. Revisa contra a issue, os critérios de aceite, as specs e os ADRs, e publica o veredito na issue.
   - **Reprovado:** o implementador corrige e uma nova revisão é feita do zero.
   - **3 reprovações:** a issue recebe o label `ready-for-human` e o trabalho para.
5. **PR e esteira:** se aprovado, o revisor abre o PR para o `develop` com `Closes #<nº>`, ativa `gh pr merge --auto --squash --delete-branch` e acompanha a CI. Ele mesmo corrige falhas e conflitos.

Regras que vieram de incidentes da semana:

- **Migrations:** a próxima migration usa o próximo número livre no `develop`. Se outra issue entrar antes, renumere no rebase. O Git **não** acusa esse conflito, porque os nomes de arquivo diferem. Sempre rode `pnpm db:migrate` num banco limpo antes do PR.
- **Modelo:** nunca aceite o diálogo do Codex que oferece trocar para outro modelo quando o limite de uso acaba. Escolha manter o atual.
- **Retomada:** depois de qualquer pausa ou limite, confira primeiro as mensagens pendentes (`orca orchestration check`) e responda as perguntas dos implementadores. Uma pergunta sem resposta travou a #19 por 1 hora.
- **Workflows:** PRs que mexem em `.github/workflows/` não entram por auto-merge e ficam para o Guilherme. Ele ainda vai decidir se isso muda.
